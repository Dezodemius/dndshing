# D&D Campaign Platform

Веб-платформа для русскоязычных игроков и мастеров **D&D 5e**: живой лист персонажа с прокачкой в духе Baldur's Gate 3, кампании-визитки и торговцы с настоящей экономикой.

Продукт работает **до и после игровой сессии**, а не во время неё. Единственный сценарий «за столом» — игрок с телефона смотрит и прокачивает лист и закупается у торговца по ссылке от мастера.

**Это не VTT.** Не замена Roll20/Foundry, не система бросков и боёвки, не опенсорс-проект.

## Статус

Проект переписывается с нуля. Прежний прототип (Next.js-генератор персонажей) удалён — задача `DND-000` закрыта. Сейчас в репозитории только документация, конвенции и агентские воркфлоу; кода приложения ещё нет.

Следующая задача — **`DND-001` · Каркас backend и окружение**. Порядок работ и зависимости — в [`.claude/docs/BACKLOG.md`](.claude/docs/BACKLOG.md), статус задач — на [доске проекта](https://github.com/users/Dezodemius/projects/11).

## Что входит в MVP

Регистрация и вход (email + Яндекс / VK ID / Mail.ru) · пошаговое создание персонажа с автоматическим расчётом модификаторов, КД, хитов · лист персонажа mobile-first: HP, инвентарь, заклинания, кошелёк · прокачка визардом с историей уровней и откатом последнего · кампании с инвайт-кодом и read-only листами для мастера · торговцы с витриной по ссылке, покупкой и продажей · импорт игрового контента JSON-паками.

Вне скоупа MVP (фаза 2+): AI-генераторы, хоумбрю-контент мастеров, мультикласс, эффекты и бафы предметов, лог транзакций, автоконвертация валют, мультиязычность, real-time. Полный список — в [`REQUIREMENTS.md`](.claude/docs/REQUIREMENTS.md) §6.

MVP считается готовым, когда владелец проведёт одну реальную кампанию (мастер + 5 игроков) полностью в системе, без единой ручной правки БД.

## Стек

Стек зафиксирован по итогам дискавери; альтернативы не рассматриваются.

| Слой | Технологии |
|------|-----------|
| Backend | Python 3.12, FastAPI, SQLAlchemy 2 (async), Alembic, Pydantic v2, pytest |
| БД | PostgreSQL 16 |
| Frontend | React 18 + TypeScript + Vite, TanStack Query, react-hook-form + zod, React Router, i18next (locale `ru`) |

## Разработка

### Команды

```bash
cp .env.example .env                # локальный конфиг: заполнить пустые значения (см. ниже)
pip install -r requirements-dev.txt # зависимости backend

docker compose up -d --build        # всё приложение: postgres + api + фронт, http://localhost:8080
alembic upgrade head                # миграции (локально, вне контейнера)
pytest                              # тесты backend
pytest --cov=app --cov-report=term-missing   # тесты backend + покрытие (htmlcov/ — отчёт в браузере)
ruff check .                        # линт backend

cd frontend && npm install                            # зависимости фронта (.env не нужен, см. frontend/README.md)
cd frontend && npm run dev                            # фронт локально, http://localhost:5173
cd frontend && npm run build                          # tsc -b && vite build
cd frontend && npm run test                            # тесты фронта (vitest)
cd frontend && npm run test:coverage                   # тесты фронта + покрытие (coverage/ — отчёт в браузере)
```

### Два режима фронта

**`docker compose up`** поднимает приложение целиком — это то же, что крутится на проде. Образ фронта многостадийный: Node собирает бандл (`npm run build`), готовую статику раздаёт nginx, и он же проксирует `/api/v1` на контейнер `api`. Браузер живёт на одном origin `http://localhost:8080` — CORS не нужен, refresh-cookie остаётся first-party. Node в финальном образе нет.

**`npm run dev`** — для разработки: Vite с hot-reload на `http://localhost:5173`, ходит на API по `VITE_API_BASE_URL` из `frontend/.env` (кросс-origin, поэтому backend отдаёт CORS-заголовки). Порты разные, так что dev-сервер и контейнер спокойно работают одновременно.

Важно: `VITE_*` переменные Vite вшивает в бандл **на этапе сборки**, а не читает в рантайме. Поэтому в образ `VITE_API_BASE_URL` намеренно не передаётся, а `frontend/.env` исключён через `.dockerignore` — иначе в собранный бандл попал бы чей-то `localhost:8000`. Без переменной клиент падает на относительный `/api/v1` (`frontend/src/api/client.ts`), который и проксирует nginx.

### Секреты

Дефолтных паролей в репозитории нет. После `cp .env.example .env` нужно сгенерировать пароль постгреса

```bash
python -c "import secrets; print(secrets.token_urlsafe(24))"
```

и подставить его в `.env` в три места: `POSTGRES_PASSWORD`, `DATABASE_URL`, `TEST_DATABASE_URL`. Пока `POSTGRES_PASSWORD` пуст, `docker compose up` не стартует, а приложение без `DATABASE_URL` падает на старте — оба варианта громкие и намеренные: тихого фолбэка на известные креды быть не должно. Порты `5432`, `8000` и `8080` публикуются только на `127.0.0.1`: наружу в проде смотрит Cloudflare и хостовый прокси, а не контейнеры.

### Ветки и задачи

База — **`develop`**. Одна задача = одна GitHub-ишью = одна ветка `feat/dnd-NNN` = один PR в `develop`. В `main` попадают только релизные мержи; прод деплоится отдельным CD-воркфлоу.

Ишью заводятся из бэклога скриптом:

```bash
python .claude/scripts/create-issues.py           # dry run
python .claude/scripts/create-issues.py --apply   # создать метки и ишью
```

`BACKLOG.md` — спецификация, а не трекер: статуса задач в нём нет. Прогресс живёт в GitHub — метки ишью (`agent-ready` → `in-progress` → закрыта, плюс `blocked`) и поле Status на доске проекта.

### Автоматизация

- `.github/workflows/agent.yml` — автономный агент: берёт ишью с меткой `agent-ready`, работает в облаке, открывает PR в `develop`. Запускается по расписанию или вручную (`workflow_dispatch` с номером ишью).
- `.github/workflows/review.yml` — независимое ревью каждого PR в `develop`; комментарии в PR, арбитр — владелец.
- `.github/workflows/cd.yml` — прод: мерж в `main` → деплой на self-hosted раннере, зарегистрированном на самом прод-сервере.
- `.github/workflows/cd-stand.yml` — стенд: push в `develop` → деплой по SSH на сервер timeweb.cloud. Через `workflow_dispatch` на стенд выкладывается любая ветка, не мержа её.

### Стенд (timeweb.cloud)

Адрес стенда не зашит в воркфлоу — он задаётся переменными репозитория (Settings → Secrets and variables → Actions), поэтому пересозданный сервер подключается сменой одного значения.

| Имя | Тип | Обязательна | Значение |
|---|---|---|---|
| `STAND_HOST` | variable | да | IP или домен стенда |
| `STAND_SSH_KNOWN_HOSTS` | variable | да | вывод `ssh-keyscan -p 22 <IP>`: ключ хоста пинится, чтобы деплой вместе с доступом к серверу не уехал к перехватившему адрес |
| `STAND_SSH_KEY` | secret | да | приватный ключ, публичная часть — в `~/.ssh/authorized_keys` на стенде |
| `STAND_USER` | variable | нет | пользователь SSH, по умолчанию `root` (как на серверах timeweb) |
| `STAND_SSH_PORT` | variable | нет | порт SSH, по умолчанию `22` |
| `STAND_PATH` | variable | нет | каталог кода на сервере, по умолчанию `/opt/dnd-stand` |

Подготовка сервера — один раз: поставить Docker с плагином compose, создать каталог и положить в него `.env` (по образцу `.env.example`, со своими `POSTGRES_PASSWORD` и `JWT_SECRET_KEY`, `APP_ENV=stand`). В репозиторий этот файл не попадает и деплоем не перезаписывается: выкладка чистит каталог, сохраняя `.env` и `docker-compose.override.yml`.

Цепочка деплоя та же, что у прода: `build` → `alembic upgrade head` → `up -d` → проверка контейнеров. Проверка ждёт, пока nginx фронта не отдаст `/healthz` через прокси на `api`, SPA-шелл и `version.json` с sha задеплоенного коммита — то есть красный чек означает, что стенд не переключился на новый деплой. Порты, как и на проде, публикуются только на `127.0.0.1`: смотреть стенд снаружи — через хостовый прокси или туннель перед `FRONTEND_HOST_PORT` (по умолчанию `8080`), а стенд-специфичные правки удобно держать в `docker-compose.override.yml` на сервере.

### Что важно помнить при работе с кодом

- Любая правка схемы БД — только миграцией Alembic.
- Деньги — три независимых целых поля (`gold` / `silver` / `copper`), никакой автоконвертации.
- Покупка и продажа у торговца — одна транзакция БД с `SELECT ... FOR UPDATE`.
- Level-up хранится дельтами (`LevelUpRecord`); откатывается только верхняя запись, поле `level` напрямую не редактируется.
- Проверка владения ресурсом — в каждом сервис-методе: IDOR — главный класс уязвимостей проекта.
- Все строки UI — через словарь i18next; хардкод русского текста в JSX запрещён.
- Комментарии в коде и тексты коммитов — на английском, пользовательские строки — на русском.
