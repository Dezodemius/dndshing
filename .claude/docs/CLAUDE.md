# CLAUDE.md

## Что это за проект

D&D Campaign Platform — веб-платформа для игроков и мастеров D&D 5e: живой лист персонажа с прокачкой в духе BG3, кампании, торговцы с экономикой. Работает до/после сессии, не VTT. Язык продукта — русский.

## Документы — читать перед любой задачей

- `.claude/docs/REQUIREMENTS.md` — ЧТО делаем и зачем: роли, сценарии US-1…US-12, границы MVP, критерии приёмки.
- `.claude/docs/ARCHITECTURE.md` — КАК: стек, доменная модель, схема БД, API-контракт, нарезка задач (раздел 11).
- `.claude/docs/BACKLOG.md` — задачи DND-NNN, их метки и зависимости.

При конфликте: business-requirements главнее в части «что», architecture — в части «как». Если реализация требует отступить от документов — остановись и спроси, документы правятся первыми.

## Стек (зафиксирован, не предлагать альтернатив)

- Backend: Python 3.12, FastAPI, SQLAlchemy 2 async, Alembic, Pydantic v2, pytest
- БД: PostgreSQL 16
- Frontend: React 18 + TypeScript + Vite, TanStack Query, react-hook-form + zod, React Router, i18next (locale: ru)
- Инфра: Docker Compose, GitHub Actions, Cloudflare

## Структура backend

`app/{core,auth,content,characters,campaigns,merchants}` — модульный монолит. В каждом модуле: `router.py → service.py → models.py + schemas.py`. Роутеры не трогают модели напрямую; между модулями — только через сервисы. Правила 5e — только в `app/characters/rules_5e.py` (чистые функции, покрыты юнит-тестами); фронт правила не дублирует, а берёт блок `computed` из API.

## Правила работы

1. Работай строго в рамках одной задачи из `.claude/docs/BACKLOG.md`. Не добавляй фичи из фазы 2 (список — в `.claude/docs/REQUIREMENTS.md` §6), даже «раз уж рядом».
2. Не выходи за модуль задачи. Нужен код в чужом модуле — только вызов его сервиса; если сервиса нет, спроси.
3. Любая правка схемы БД = миграция Alembic. Правок схемы вне architecture.md §5 не делать без согласования.
4. Деньги — три независимых integer-поля (gold/silver/copper), НИКАКОЙ автоконвертации.
5. Покупка/продажа у торговца — одна транзакция БД с блокировкой (`SELECT ... FOR UPDATE`).
6. Level-up только через дельты (LevelUpRecord), откат — только верхней записи. Поле level напрямую не редактируется.
7. Проверка владения ресурсом (персонаж, кампания, торговец) — в каждом сервис-методе. IDOR — главный класс уязвимостей проекта.
8. Все строки UI — через i18next-словарь, хардкод русского текста в JSX запрещён.
9. Тесты обязательны для: rules_5e, покупки/продажи (недостаток средств, конкурентность), level-up/rollback, прав доступа.
10. Комментарии в коде и тексты коммитов — на английском; пользовательские строки — на русском (в словаре).
11. База — develop; в `main` только релизные мержи.
12. Секретов в репозитории нет: ни паролей, ни ключей, ни «дефолтов на всякий случай» — ни в коде, ни в `docker-compose.yml`, ни в `.env.example`. Отсутствие секрета обязано ронять старт (`Settings` без дефолта, `${VAR:?}` в compose), а не подставлять фолбэк — тихий фолбэк на известные креды уезжает в прод.

## Команды

```bash
cp .env.example .env                              # локальный конфиг (не коммитить)
python -c "import secrets; print(secrets.token_urlsafe(24))"   # пароль БД: подставить в POSTGRES_PASSWORD и оба URL
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements-dev.txt                # зависимости backend + dev-инструменты

docker compose up -d db                            # только Postgres, если api гоняешь локально
alembic upgrade head                                # миграции на основную БД
uvicorn app.main:app --reload                       # backend локально, http://localhost:8000/healthz

docker compose up -d --build                        # весь стек: api + postgres в контейнерах

pytest                                               # тесты backend (сами применяют миграции к тестовой БД)
ruff check .                                         # линт backend

cd frontend && npm install && npm run dev             # фронт локально, http://localhost:5173
cd frontend && npm run build                          # tsc -b && vite build
```

## Definition of Done задачи

- Критерии приёмки из промта задачи выполнены и проверяемы.
- Тесты написаны и проходят; `pytest` зелёный целиком.
- Миграции применяются с нуля (`alembic upgrade head` на пустой БД).
- `.claude/docs/BACKLOG.md` обновлён, **если менялись скоуп, зависимости или метки** задачи. Статус в BACKLOG не проставляется — см. «Где живёт статус задачи».
- Ничего из фазы 2 не просочилось.

## Где живёт статус задачи

Источник статуса — GitHub, не файлы репозитория:

- метки ишью: `blocked` → `agent-ready` → `in-progress` → `in-review` → закрыта. Сбоку — `agent-deferred`: прогон сорвался (лимит модели, таймаут, падение), задача выпала из очереди до следующей ночи;
- поле **Status** на доске проекта (Todo / In Progress / Done): https://github.com/users/Dezodemius/projects/11

`BACKLOG.md` — спецификация задач (скоуп, зависимости, критерии приёмки), а не трекер. Статус в нём не дублируется намеренно: формата под него нет, `create-issues.py` его не парсит, и правка статуса в каждом PR превращала бы файл в постоянный конфликт при параллельных ветках `feat/dnd-NNN`.

## Конвейер BACKLOG → GitHub

Единственный машиночитаемый граф зависимостей — строки `depends:` в BACKLOG. В телах ишью задачи упоминаются прозой, парсить их как зависимости нельзя.

| Скрипт / воркфлоу | Что делает | Когда |
|---|---|---|
| `.claude/scripts/create-issues.py --apply` | новые `### DND-NNN` из BACKLOG → ишью + метки. Существующие ишью не трогает | вручную, после добавления задач |
| `.claude/scripts/plan-tasks.py --apply` | граф `depends:` → метки `agent-ready` / `blocked`; доска: Эпик, Область, Status. С `--clear-deferred` ещё и снимает `agent-deferred` — новая ночь, новая попытка | `plan.yml`: создание/закрытие ишью, push в BACKLOG, cron 23:50 UTC (`--clear-deferred` — только на cron) |
| `.github/workflows/agent.yml` | берёт первую свободную `agent-ready`, вешает `in-progress`, гонит агента, открывает PR, меняет метку на `in-review` | cron каждые 20 минут в окне 00:00–05:59 UTC |
| `.github/workflows/done.yml` | PR влит → ишью закрыта, метки цикла сняты | мерж или закрытие PR в develop |

Метку `agent-ready` руками не ставят — её выдаёт планировщик, когда все зависимости закрыты. `in-progress` и `in-review` принадлежат агенту, планировщик их не трогает.

### Ночной цикл

Прогон = одна задача. Cron будит воркфлоу каждые 20 минут, `concurrency: agent` выстраивает прогоны в очередь по одному — за ночь агент делает задачи подряд, пока не кончится очередь, окно или квота модели.

Что делает ночь конечной:

- **Лимит модели.** Отличить его от обычной поломки по логу нельзя, поэтому любой сорвавшийся прогон вешает на задачу `agent-deferred` и выбывает. Когда так выбыло `MAX_DEFERRED` (2) задач — это уже не совпадение, а квота: агент до утра не берёт ничего. Утром `plan.yml` снимает метки, и задачи едут заново.
- **`MAX_OPEN_PRS` (3).** Задачи ночи независимы по графу `depends:`, но ветки режутся от `develop` и кода друг друга не видят. Чем больше PR висит немёрженными, тем выше шанс конфликта (миграции, общие файлы). Разгребли утром — ночью поедет дальше.
- **Окно.** Прогон, вытолкнутый очередью за 06:00 UTC, новую задачу не берёт: днём квота нужна человеку.

Зависимую цепочку за одну ночь агент не пройдёт: `agent-ready` даётся только по **закрытым** зависимостям, а закрывает ишью мерж PR — то есть человек. За ночь делаются независимые задачи.

## Команда «исправить» в PR

Комментарий к PR, начинающийся со слова **`исправить`** (или `/fix`), запускает `fix.yml`: агент собирает замечания ревьюера, правит их в ветке PR, гоняет `ruff` и `pytest` и пушит. Дальше цепочка замыкается сама:

```
комментарий «исправить» → fix.yml (правки + push под GH_PAT)
                        → synchronize → review.yml (по каждому замечанию: исправлено / частично / нет)
```

- Можно уточнять скоуп прямо в команде: «исправить только 1 и 3», «исправить, тесты не трогай» — уточнение главнее списка ревьюера.
- Замечание, которое агент считает ошибочным, он не правит, а пишет возражение в отчёте — арбитр всё равно человек.
- Команду понимает только комментарий **человека** с правом записи и только как **первое слово**. И то и другое — защита от петли: отчёты и вердикты пишут боты, а фраза «нужно исправить X» в теле замечания иначе перезапускала бы пайплайн сама на себя.
- PR из форка не поддержан: агенту некуда пушить.

Доска — Projects v2 у пользователя, поэтому `plan.yml` ходит под `secrets.GH_PAT` (у `GITHUB_TOKEN` нет scope `project`). Доска — витрина, очередь — метки: если доски нет, токен без scope или на ней не заведены поля `Эпик` / `Область` (single-select, опции — точь-в-точь как в `backlog.py`), планировщик пишет предупреждение и идёт дальше. Метки проставятся, воркфлоу зелёный.

Парсер BACKLOG и планировщик покрыты тестами (`.claude/scripts/test_backlog.py`, гоняются в `plan.yml`): сломанный парсер разметил бы очередь мусором, поэтому падать он должен до записи в GitHub.
