# Security review

## IDOR — главный класс уязвимостей проекта
Каждый эндпоинт с ресурсом проверяет владение В СЕРВИСЕ, не полагаясь на фронт:
- персонаж: `character.user_id == current_user.id` — во всех CRUD, inventory, spells, level-up, а также в `buy`/`sell` (нельзя купить чужому персонажу и продать чужой предмет);
- кампания: изменение/инвайт/kick — только `dm_user_id`; read-only лист персонажа — только DM этой кампании и только для присоединённого персонажа;
- торговец: изменение — только `owner_user_id`;
- inventory_entry в sell обязан принадлежать указанному character_id, а тот — текущему пользователю (двухзвенная проверка).
Чужой ресурс → 404 (не 403), чтобы не раскрывать существование id.

## Деньги и сток
- Покупка и продажа — одна транзакция БД с `SELECT ... FOR UPDATE` на строках персонажа и позиции торговца.
- Проверка средств и стока — внутри транзакции, после захвата блокировки.
- Отрицательные quantity/суммы отклоняются валидацией до сервиса.

## Auth
- Пароли — argon2; JWT access ≤ 15 мин; refresh — httpOnly + Secure + SameSite cookie, с ротацией.
- OAuth state-параметр обязателен; redirect_uri — только из белого списка конфига.
- Rate-limit на /auth/* и /shop/*/buy.
- Токены/секреты не логируются; в тестовых фикстурах — фейковые значения.

## Общее
- Никакого сырого SQL со строковой подстановкой — только параметры SQLAlchemy.
- `is_admin`-эндпоинты проверяют флаг в зависимости, не в роутере по условию.
- Ответы ошибок не содержат stack trace и внутренних путей.
- Загружаемый контент-пак валидируется схемой до записи; размер запроса ограничен.

## Формат применения при ревью
Пройди diff по каждому пункту выше; для каждого затронутого эндпоинта явно ответь: «владение проверено в <файл:строка>». Если проверки нет — это блокер, не замечание.
